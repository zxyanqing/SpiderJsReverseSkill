# 环境发现协议

什么时候读本文件：处理静默缺失与存在性探测、从零首轮该收集什么、区分追踪诊断与正式验收、或判断补丁是否超出最小契约时。

本文件是 **静默四类记录、四类补环境错误、最小契约、首轮模板、追踪三模式** 的权威位置。跨层画像与值来源见 `references/fingerprint.md`；无浏览器启动路径见 `references/workflow.md`；验收三状态/三维度见 `references/validation.md`。

## 静默探测四类

首跑与诊断须覆盖下列不会必然抛异常的探测（与普通调用失败分开记）。每条记录只保留：属性名、对象类别、操作类型、次数、返回类型；**不**记录 Cookie、令牌或完整计算结果。

1. **普通读取与方法调用**：属性 get、方法调用及返回类型。
2. **存在性查询**：`prop in object`、`Object.hasOwn`、原型链上的 `hasOwnProperty` / 继承查询。
3. **对象形状**：`Object.getOwnPropertyDescriptor`、枚举性、可配置性、getter/setter 形态。
4. **类型与反射检查**：`typeof`、`Object.prototype.toString`、`instanceof`、函数 `name` / `length` / `Function.prototype.toString`。

诊断须能区分：

| 状态 | 含义 |
| --- | --- |
| 未读取 | 本路径未观察到对该属性的上述操作 |
| 读后 `undefined` | 已读取，结果为 `undefined`（属性可能存在） |
| 仅通过存在性检查 | `in` / `hasOwn` 等为真，但未完成契约所需的读取或调用 |

没有 `ReferenceError` **不等于** 接口契约完整。对象形状检查单独成类记录，不得并入「缺 API」一笔带过。

## 四类补环境错误

每个候选问题在实验报告中使用统一分类（不得都写成「缺少 API」）：

| 类别 | 典型表现 | 修复重点 |
| --- | --- | --- |
| 存在性 | 属性不存在 | 增加最小对象或 getter |
| 类型 | 类型错误（如应为数组却返回字符串） | 修正返回类型与转换规则 |
| 结构 | `instanceof`、原型、brand 或 descriptor 不同 | 修正原型、brand、getter/setter 与函数形态 |
| 值一致性 | JS / HTTP / TLS / 时区等画像互相矛盾 | 统一来源，禁止各层单独改「看起来对」的值 |

每次实验报告必填：

- 问题类别（上表之一）
- 观察证据（含静默探测摘要）
- 修改的契约层（存在性 / 类型 / 结构 / 值）
- 结果是否支持原假设

值一致性的跨层细则见 `references/fingerprint.md`「跨层画像一致性」；本表只要求分类，不在此复制四层画像清单。

## 最小契约与反过度补环境

「补最小契约」指：只补当前路径 **有访问证据** 或 **标准契约明确要求且已被验证** 的部分。

- 没有访问证据的 API **不优先**实现；不因「常见」无条件加入。
- 先补被实际读取的属性，再补其被验证的结构（descriptor / 原型 / brand）。
- 只实现脚本用到的 `plugins`、`mimeTypes`、`chrome` 等子集；不因 UA 含 Chromium 就伪造完整 `window.chrome`。
- **不**一次同时修改 UA、窗口尺寸、插件、TLS 客户端与请求头等多层画像；成套切换须走声明配置（见 fingerprint），且仍按单次假设可区分。
- 每个补丁必须声明解决的是存在性、类型、结构还是值一致性（见上表）。

验收：补丁有访问证据或标准契约依据；补丁增多时，诊断覆盖与真实消费方验收应同步改善，而不是只增加本地通过项。对象反射实现细节见 `references/env-object-model.md`；最小范围规则以本节为准。

## 存在性与过度暴露 / 保持缺失

读到属性访问 **不等于** 必须在本地补上该属性。发现访问后须回答：

1. 参照浏览器中是否存在、在哪个页面上下文？
2. 目标如何检查/消费（`in`、own、原型、descriptor、取值）？
3. 本地与参照是否不同？

三分支：

| 决策 | 含义 |
| --- | --- |
| **实现必要契约** | 参照存在且目标消费该契约；按最小契约补齐 |
| **保持缺失** | 参照中不存在（或仅特定上下文存在而当前路径不应有）；本地不得补占位 |
| **证据不足继续调查** | 探针只读值不够；查 `in` / own / 原型 / descriptor；临时 getter 须标为干预，不得当未插桩基线 |

「存在性错误」覆盖 **过度暴露**：参照不存在却补了占位（如无证据伪造 `chrome`）。未观察到访问 ≠ 浏览器不存在；反之亦然。合成回归见 `tests/presence-keep-missing.test.js`（T-G3）。

## 首轮操作模板

从零或证据不足时，按下列固定顺序推进（可与默认主线并行，但不得跳过报告字段）：

1. 明确目标消费方和成功条件。
2. 运行原始脚本，保存异常、输出摘要、导航、Storage 与请求记录（模式见下文「追踪三模式」）。
3. 列出已知、未知、假设和未验证项。
4. 记录实际访问的 API、存在性探测和对象形状检查（静默四类）。
5. 对每个候选属性标记来源（确定 / 假设 / 未知；细则见 `references/fingerprint.md`）。
6. 只补最小契约。
7. 运行本地集成与回归。
8. 用真实消费方验证。
9. 若被拒，记录支持、削弱或排除的解释。
10. 连续无进展后做宏观复核，不继续盲目堆补丁（被拒固定清单见 `references/env-debug-loop.md`，若尚未写入则以三类进展更新为准）。

### 首轮报告必含字段

- 入口和消费点
- 运行时和脚本输入摘要
- API 访问和异常摘要（含静默四类）
- 已知 / 未知 / 假设表
- 当前最小补丁及其依据（对应哪一类错误）
- 本地结果与真实消费方结果（分列；本地通过 ≠ 接受）
- 下一项可区分候选解释

## 追踪三模式

访问记录与诊断钩子可能改变 descriptor、对象身份、调用顺序或异常，从而污染反仪器化检测。必须分离三种模式：

| 模式 | 要求 |
| --- | --- |
| **基线** | 无插桩、无 Proxy/eval 包装、无额外诊断日志；用于观察原始行为 |
| **追踪** | 仅在有具体诊断问题时 **最小范围** 启用；只产出候选解释与元数据；记录钩子是否改变 descriptor、身份、顺序或异常；尽量在原型/边界做可恢复包装 |
| **正式验收** | 关闭 Proxy、eval 包装、变量改写与额外诊断日志；**不**加载访问追踪包装；诊断结束后已恢复全部全局改动 |

约束：

- 追踪层与正式执行层分离；追踪结果只保存元数据，不把钩子环境当作交付环境。
- 正式验收必须使用未注入诊断钩子的环境。
- 追踪结果 **不能**单独证明「未插桩路径等价」。
- 「带访问记录运行」默认指：先基线，再按需进入追踪；**交付与消费方验收走正式模式**。

与 fixture/Trace 工具的关系见 `references/fixture-and-trace.md`；工具打开追踪能力时仍须遵守三模式，不得把诊断包装带进正式验收。
