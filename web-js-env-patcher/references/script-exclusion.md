# 脚本排除实验（按需专项）

什么时候读本文件：已有完整可跑基线，且有明确优化需求（缩短路径、缩小依赖面）时，才考虑按单元跳过脚本。**不是**每任务门槛；对照不明或结果变坏时保留完整执行。

合成回归（可执行断言）见 `tests/script-exclusion.test.js`（T-G7）。

## 何时启用

- 仅在有明确优化需求时启用（例如证明某段脚本与消费结果无关）。
- 先完整执行得到基线产物与必要状态，再做排除对照。
- 没有可比基线、或排除后无法解释差异 → **不要**排除。

## 实验规则

1. **每次只跳过一个脚本单元**（初始化依赖、无关脚本、提交调用等按任务拆分；单元边界写进项目记录）。
2. 比较消费结果 / 导航意图 / 必要会话态与基线。
3. 不可比因素（随机挑战、时间戳、服务端轮换）如实说明；不能假装同一对照。
4. **对照不明**或跳过后目标结果变坏 → 结论为**保留完整执行**，并写明原因。
5. **禁止**仅凭函数名、代码位置或「像调试代码」直接删除脚本。

## 典型三类单元（合成页最小模型）

| 单元 | 作用 | 跳过时期望 |
| --- | --- | --- |
| 初始化依赖 | 建立消费所需状态 | 消费行为或必要状态出现差异 |
| 无关脚本 | 不参与目标产物 | 目标结果与完整执行等价（相对任务目标） |
| 提交调用 | 写出最终可消费结果 | 识别到结果缺失 |

项目侧如何拆单元由当前目标决定；本 Skill 只沉淀方法与合成证明，不规定真实站点的脚本名单。

## 与 workflow 的关系

日常推进仍以完整路径为准（见 `references/workflow.md`）。本专项是可选加速/证明手段，启用后仍须能回到完整执行验收。
