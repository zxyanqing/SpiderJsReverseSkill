# 请求链、会话与网络

什么时候读本文件：请求被拒、需要核对 Cookie/会话链、目标 JS 内部 XHR/fetch、传输差异、challenge / verify、**同会话挑战输入原子包**，或 Node 页面 Realm 与宿主 HTTP CookieJar 交接时。

## 挑战输入原子包

**定义按「同次响应链的实际依赖闭包」，不是固定字段表。**

- **基线成员（常有）**：挑战 HTML、初始化/外链/入口等实际加载的脚本、最终页面 URL、UA、页面脚本可见 Cookie 视图。
- **按依赖扩包**：若目标读取或消费方依赖响应头、重定向链结果、Client Hints、Storage、其它会话态等，这些也必须纳入 **同一次** 关联输入；缺一则失败，禁止静默用历史产物补洞。
- 禁止隐式回退旧动态脚本/旧落盘文件。优先 stdin/内存结构化对象；临时文件须本次独占、生命周期受控。
- 可记摘要与会话关联 ID；**报告/stdout/普通日志不写 Cookie 值或令牌**。

每份 Node 输入须能关联到唯一的本次响应链；缺少任一必需成员时明确失败。

## Realm ↔ HTTP（CookieJar）

页面 Realm 与宿主 HTTP 会话模拟同一浏览器的不同边界，不得混职责：

| 层 | 职责 |
| --- | --- |
| **宿主 / HTTP** | 会话、**会话 CookieJar**（按 Domain/Path/Secure/SameSite/过期/同名覆盖等作用域规则）、重定向、最终响应 |
| **页面 Realm** | 仅当前 URL 下浏览器脚本可见的 Cookie 子集；**HttpOnly 永不进入** `document.cookie` |

- 脚本 `document.cookie` 写入可能与某条 HttpOnly **同名但作用域不同**：Jar 必须按作用域并存/覆盖，**禁止**用字符串拼接把可见 Cookie「盖住」或删除 HttpOnly。
- Node → 宿主交接用结构化三元组：**导航 URL + 导航发生时的状态快照 + 待合并的脚本 Cookie 增量（结构化，非裸 header 串）**；三者配对。
- **敏感原值通道**：完整 Cookie 原值（含 HttpOnly）只经受控私有通道交给消费方/HTTP 客户端（进程内对象、加密临时句柄等）；**不得**出现在 stdout、实验报告、stage markdown、评测可见材料。
- HTTP 层用 CookieJar API 合并后再请求导航目标。
- 只有最终 HTTP 消费方接受才算成功；**生成 Cookie / 脚本成功 / 服务端接受**分报。

## 请求链与会话

目标网站的页面、资源、挑战、参数生成和最终请求可能共享 Cookie、Storage、Header 或连接状态。观察实际顺序与更新点，记录每次请求所在的会话和来源。没有证据时不要假定每个项目需要同一 Session。

目标 JS 内部 XHR/fetch 与本地外部请求编排分开建模。若两者需共享状态，明确持有者、同步点和错误路径；若目标只生成本地参数，则网络桥接可标为不适用。比较请求时保留方法、URL、携带数据、响应和时间线，关联到网站实际接受或拒绝。

本地产物生成、保存和实际发送分别核对。关联本次输入、代码版本、产物来源、选取时点、出站数据和响应，浏览器参照成功与本地成功分开。HTTP 200 可能是挑战页或应用外壳，按任务观察预期资源、数据或业务行为。响应状态码本身不指认某个 API 或传输参数为根因。

消费动作附近的 URL、Cookie/Storage 与必要请求状态应对应同一时点，不能分别取各自最后值就假定匹配。导航意图、提交与后续更新区分记录；多个候选结果通过实际消费关系和有区分力的实验选择，不默认最早或最晚。

相同失败反馈没有新增信息时，重新检查会话/输入、执行分支、输出边界与传输假设，再决定下一实验。采样、暂停、版本、时钟等混杂因素按可比范围记录；不机械逐字段枚举，也不将任意字段差异直接当原因。单次接受不等于完成；按验收等级做必要的新输入或新会话复验（默认 L2 = 消费接受 + 稳定性，真实性独立，见 `references/validation.md`「验收等级」）。L2 复验计入在线护栏 G2 预算；触发 G3 时停止复验并如实报告当前等级与三维度，见 `references/workflow.md`「预算、护栏与路线退出」。

## 在线验证记录

每次携带本地产物的在线验证（含验收等级复验）记录同一套字段，供护栏 G7 引用，不另设格式：

| 字段 | 含义 |
| --- | --- |
| 时间 | 发起验证的时刻 |
| 目标 | 授权范围内的站点与接口 |
| 产物来源 | 本次本地执行的入口、代码/资源版本、选取时点 |
| 响应摘要 | 状态码、是否接受/拒绝、关键业务字段或挑战迹象（敏感值脱敏） |

需要更深对照时，在同一记录中补充输入、出站数据、会话与时间线；与上文「请求链与会话」的核对要求一致。

## 目标 JS 内部 XHR/fetch 语义

只有目标路径实际调用 XHR、fetch 或相关网络 API 时，才对浏览器与本地实现比较。关注请求构造、Header/Body、actor/Realm、事件与 Promise 顺序、超时/错误、status、responseURL、响应体及 reload 后状态。按目标实际消费的字段选择深度。

no-send transcript 可验证构造和调度路径，但不证明真实响应。用于严格对照的浏览器/Node transcript 记录采集来源、资源版本与实际 observation；缺失字段或执行失败如实呈现。运行 `check_xhr_fetch_semantics.js --help` 查看格式和明确的 `--require` 选项。

若目标 JS 不调用这些 API，即使外层脚本另行发请求，也无需该检查。

## XHR/fetch 与请求会话的桥接

当目标 JS 内部网络调用需要与外部执行器共享 Cookie、响应或连接状态时，设计清晰的会话持有者及桥接接口。记录请求发起方、Cookie/Storage 同步、响应与异常回传、生命周期及资源清理。Python `curl_cffi`、Node 客户端或其他实现按项目现有路径选择。

`check_xhr_fetch_session_bridge.js` 可诊断对应桥接。其 `--require-live` 仅适用于当前目标确有 live JS 网络调用的情况；不能因为外部脚本发 HTTP 请求就声称目标 JS bridge 已存在。

若目标代码只生成参数且无内部网络调用，桥接不适用；网站请求由交付入口另行编排并单独验证。

## 传输与网站反馈

目标网站拒绝本地生成的结果时，传输特征是候选原因之一。先确认参数生成、资源版本、会话、Header/Cookie 与请求顺序，再用可区分的实验判断 TLS/HTTP2、UA/Client Hints 或代理差异是否相关。状态码或 challenge 页面本身不能唯一定位传输原因。

请求客户端按用户约束和目标行为选用，可能是已有客户端、TLS 指纹兼容库或无真实请求的离线模式。选用 TLS 客户端或改 Header 时，须与当前 JS/CH 声明画像一致，见 `references/fingerprint.md`「跨层画像一致性」。目标 JS 内部网络调用另见上文「目标 JS 内部 XHR/fetch 语义」；外部请求客户端的存在不证明 JS XHR/fetch 语义。网站真实响应与本地工具检查分别记录。

## Cookie 与状态生成链

Cookie 可能由服务器、目标 JS、页面事件或已有会话生成，也可能在请求后刷新。先观察写入者、作用域、有效期和消费点，再判断本地运行需要实现读取、写入还是同步。失效 Cookie 不自动说明 JS 环境错误。合并、覆盖与可见性一律走上文 **CookieJar 作用域规则** 与私有通道；不要用手工拼接 Cookie 头字符串代替 Jar。

对登录态、非登录生成状态及一次性 challenge 状态分别记录来源和当前有效性。旧请求样本提供结构线索，不能作为未来请求的固定状态值；动态挑战输入须满足上文「挑战输入原子包」。

## 多次写入与候选试验

当同一挑战路径对 Cookie（或等价会话态）有**多次写入**，且不确定哪一次前缀被消费方接受时，按需做候选试验（**非**每项目门槛，也**禁止**把「第 2 次」写成 Skill 默认）：

1. 记录每次写入及有序前缀；候选 n = 回放第 1…n 次状态变化，**不只**提交第 n 条赋值。
2. 与触发 URL、导航/消费时点配对；用 CookieJar 按目标 URL 算 Domain/Path/Secure/HttpOnly 可见性。
3. 每次试验恢复客户端会话基线；说明无法撤销服务端已变状态。
4. 一次性挑战按需取新挑战；不同输入不可称为完全相同对照。
5. 找到接受结果后停止无意义试发；按任务稳定性要求复验。
6. 成功选择规则写入**项目配置**并说明适用范围；缺失/重复/结构变化 → 明确失败，**不**默默取最后一次。

导航后的写入不得回填到导航前提交的候选。合成回归见 `tests/cookie-candidate-trials.test.js`（T-G4）；集成指针见 `references/integration-self-check.md`。

## Challenge 与 verify 流程观察

涉及挑战页、验证码或 verify 接口时，先识别目标代码在触发、展示、交互、提交和响应中的位置。观察页面阶段、动态资源、状态更新、输入事件和网站返回，避免只取单个参数样本而丢失消费链。

本地补环境只覆盖当前任务所需的原始 JS 行为。网站返回的挑战、成功或失败是事实，不能从本地参数长度或检查器状态推断已通过。交互可能涉及 `isTrusted` 或用户完成的页面动作，按当前工具和任务条件记录其来源。
