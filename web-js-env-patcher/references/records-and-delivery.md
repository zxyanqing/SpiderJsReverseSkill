# 任务输入、记录与交付

什么时候读本文件：整理任务输入、实验记录、代码变更记忆、交付总结、交付模板，或清理 case 证据与临时文件时。

## 任务输入与可行动作

输入可以从 URL、原始 JS、请求样本或现有代码任一材料开始。记录材料来源、当前目标、消费结果和已明确的技术/网络约束。未知字段保持未知，按实际依赖补充。

| 项目 | 当前值或未知 | 下一步观察 |
| --- | --- | --- |
| 目标页面与触发动作 |  |  |
| 原始 JS 与加载顺序 |  |  |
| 本地运行入口 |  |  |
| 产物和消费方 |  |  |
| 网站接受条件 |  |  |
| 会话、配置与资源版本 |  |  |

只有 URL 时观察页面和资源；只有 JS 时先定位入口并试跑；只有请求样本时识别动态字段和生成线索。缺少成功样本不等于不能分析，缺少真实响应时最终写“尚未验收”。可用 `scripts/check_intake.js --input task.md --json` 提取已知和未知；它不承担开工审批。

## 实验与阶段记录

报告用于恢复当前思路，数量和语言由项目决定。一次记录包含主要假设、证据与来源、改变项/保持项、原始目标路径结果、网站反馈或未验收原因、判断更新和下一步。历史记录与当前状态分开，避免旧建议被当成当前命令。

`scripts/write_stage_report.js --case-dir case --stage 实验记录 --data experiment.json` 生成简短 Markdown；`--input` 可写入已有草稿，`--append` 追加。`scripts/check_stage_reports.js` 默认诊断，显式 `--require-stage` 或 `--require-dynamic-fields --strict` 才验收选定报告。

报告里用“事实、推断、未知、局部验证、网站接受/拒绝”明确结论层级。不因缺少 Trace、addon 或网络章节而自动判整项目失败。

当前状态围绕一个总目标，分别记录事实、候选解释、未验证前提、可区分实验、实现进展、定位进展、消费方反馈、自主下一步及理由。`write_stage_report.js --data` 可用 `subtaskContribution`、`assumptions`、`alternatives`、`predictions`、`implementationProgress`、`diagnosticProgress`、`nextReason` 表达这些内容；字段可按实验需要选择，旧输入仍兼容。

报告生成不终止工作。一轮内继续执行有意义的修复与验证；用户采用逐轮授权且本轮结束时，提供可直接恢复的自主选择。交接细则见 `references/workflow.md`；授权规则见 `SKILL.md`。未完成状态与最终交付分开。

## 可恢复的代码变更记录

复杂 case 可用 `notes/代码变更记忆.md` 记录关键文件、假设、证据、改动、目标路径结果和网站反馈。历史失败是下一轮线索，不是永久禁令；新证据出现时说明为何修订原判断。

`scripts/check_change_memory.js --init` 可生成中性记录文件，`--changed` 可查询相关文件是否提到。只有任务明确选择记录完整性验收时使用 `--require-entry --strict`。变更记录不代替运行与网站反馈。

## 交付总结

简要说明本地入口、目标代码版本、所需环境组件、输入/输出、实际运行方法和观察到的网站反馈。列出局部 fixture/检查覆盖、尚未知晓的行为及适用配置。网站尚未验收时明确写出，不以“无异常”或检查通过代替。

必须写明**达到的验收等级**（L1 / L2 / L3，定义见 `references/validation.md`「验收等级」）、**三维度状态**（消费接受 / 稳定性 / 数据真实性：`已验证`|`未验证`|`不适用`）及对应证据：会话数、成功数、资源版本（URL、哈希、获取时间）；真实性有核对时另附比对摘要。只达到 L1 时，必须如实写成「单次接受」，不得写成任务完成。真实性未验证 **不**强制降为 L1。

总结对照原始总目标；实现进展、原因定位和消费方接受分别说明。总体未完成的一轮仅作进度交接，保留已试解释、未验证前提、自主选择的下一动作及理由。写完报告或局部子任务不作为提前结束完整任务的条件。

按实际路径说明状态来源、动态资源、网络职责与特殊 native 能力。无目标 JS 内部 XHR/fetch 时无需 bridge 章节；没有 Trace 时无需 Trace 闭环章节。只有任务要求详细审计时附对应矩阵和原始证据链接。

`scripts/check_final_artifact.js` 检查本地执行入口与样本动态值直接复用。`--file` / 显式入口会**纳入**样本扫描集合（不仅检查入口存在）；可用 `--source` 追加授权范围内的正式源码清单。报告区分「入口存在」与「入口内容已检」，并列出实际扫描文件。**零个可扫描源码不得 `passed`**（`insufficient-evidence`）。`--strict` 验收已选差异；`--require-final-summary` 可额外要求 `result/最终项目总结.md`。工具不会判定网站接受。合成反例见 `tests/check-final-artifact-entry.test.js`（T-G8）。

## 本地交付模板

根据项目实际运行方式填写：

```text
入口：<本地 JS 执行命令或函数>
原始脚本与版本：<文件/资源来源>
输入：<参数、配置、会话状态>
输出及完成边界：<同步、Promise、事件、导航、网络等>
环境组件：<当前路径实际使用>
本地验证：<命令与结果>
网站反馈：<接受 / 拒绝 / 未验收 / 暂不可达>
达到的验收等级：<L1 / L2 / L3>；三维度：消费接受=<>；稳定性=<>；数据真实性=<已验证|未验证|不适用>；证据：<会话数、成功数、资源版本；真实性摘要可选>
已知适用范围与下一步：<证据支持的条件>
```

运行时布局沿用项目已有结构。最终入口默认本地执行原始 JS；若任务明确选择浏览器后端，另述其职责和适用条件。自动化取证脚本可与交付代码分开放置，具体交付由用户任务决定。

## 证据与临时文件

将原始脚本、网站观察、fixture、实验记录与临时 probe 分开。交付时说明哪些文件用于运行，哪些只支持诊断；按当前任务需要清理过期临时产物。清理前识别仍用于复现、验收或恢复修改的证据。

Cookie、Token、Profile 等材料的保存与删除依当前用户意图和工作环境处理；输出报告时可脱敏。删除证据不应使当前结论失去可核查来源。

`clean_case.js` 统一以真实 case 根路径判断边界，所有遍历、直接候选、重试和空目录清理不进入符号链接。单独扫描到的链接本身也默认保留（含断链、祖先链接和环）；被选中整目录删除时只移除其中的链接本身；case 根目录是链接则拒绝，父路径的系统别名先规范化为真实路径。dry-run 与执行共用边界判断，但预览不会模拟删除后新形成的空目录。临时目录整体删除时使用 Node 的不跟随链接删除语义，目录内链接目标不被删除。
本工具用于静止的本地 case，不保证对抗并发进程在检查后交换链接的竞态；清理期间应停止该目录的写入者。
